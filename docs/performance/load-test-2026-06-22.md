# GastosAI — Pre-Launch Load / Performance Report

_Date: 2026-06-22 · Target: master @ 0.55.0 · Tool: `scripts/loadtest.mjs` (dependency-free Node, keep-alive)_

**Goal:** confirm the app can serve a meaningful volume of users before a public launch, and find
the first bottleneck.

**Environment caveat (important):** this run is against the **local dev stack** — backend via
`mvnw spring-boot:run` (un-tuned JVM, no AOT/CDS) and **local Docker Postgres**. Numbers are useful
for *relative* comparison and bottleneck-finding, **not** as absolute production capacity. Re-run
against the Oracle ARM VM + Supabase before high-traffic events.

AI endpoints were **excluded** (external-latency + per-call cost; they are quota/rate-limited and
cost-bound, not throughput-bound — see the pricing memo).

---

## 1. Results — concurrency 50, 500 requests/endpoint, **0 errors**

| Endpoint | RPS | avg | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|
| `GET /expenses/page?size=50` | 135 | 355 ms | 282 | **1057** | 1164 | 1268 |
| `GET /budgets/summary` | 300 | 160 ms | 158 | 253 | 326 | 393 |
| `GET /budget-rules/summary` | 408 | 118 ms | 115 | 201 | 264 | 298 |
| `GET /expenses/report/category` | 531 | 93 ms | 96 | 123 | 160 | 177 |
| `GET /user/entitlements` | 475 | 102 ms | 100 | 185 | 242 | 299 |

Warm-up at concurrency 10 was healthy (p95 40–130 ms across the board). 0 failed requests at 50
concurrency = the stack is **stable under load**; the issue is **latency under contention**, not errors.

Dataset: 393 expenses. Indexes verified present: `idx_expenses_user_date (user_id, date)`,
`idx_expenses_user`, `idx_expenses_category` — so the slow endpoint is **not** query/index-bound.

---

## 2. Analysis — the bottleneck is the DB connection pool, not the queries

- The slowest endpoint (`/expenses/page`, p95 ≈ 1 s) runs **two** queries (count + page) and holds a
  connection longer than the single-query endpoints; under 50 concurrent requests they queue.
- Root cause: **HikariCP is at its default `maximum-pool-size = 10`** (no pool tuning in
  `application.properties`). With 50 concurrent requests, ~40 wait for a connection → tail-latency
  spikes. This is the primary scaling lever.
- `materializeRecurring` previously wrote rows on the `/budgets` read path; the 0.55.1 storage guard
  bounds it (≤ next month), removing unbounded write-amplification under load.

---

## 3. Recommendations (ordered by impact)
1. **Tune the connection pool + use a DB pooler.** Set `spring.datasource.hikari.maximum-pool-size`
   (e.g. 20–30) **and** route prod through Supabase's connection pooler / PgBouncer (transaction
   mode) — Supabase's free tier caps *direct* Postgres connections (~60), so a pooler is required to
   serve many concurrent clients. This single change addresses the p95 spike.
2. **Cache read-heavy aggregates.** `/expenses/report/category` and the insight endpoints are good
   Caffeine-cache candidates (insights are already cached); short TTLs cut DB load sharply.
3. **Horizontal scale is already viable:** JWT is stateless and the rate limiter has an opt-in Redis
   shared store (`RATELIMIT_REDIS_ENABLED`). To scale out, run a 2nd backend instance behind Caddy
   with Redis enabled. The current single Oracle ARM VM is the present ceiling.
4. **Right-size the JVM on the ARM VM** (heap, `-XX:+UseG1GC`/`+UseZGC`, container memory limits) and
   prefer a production build over `spring-boot:run`.
5. **Re-test against production** (`scripts/loadtest.mjs <prod-token> 50 500` pointed at the prod URL)
   — local dev numbers omit prod network + Supabase latency.
6. **AI cost, not throughput, is the scale risk** for AI features: monitor `ai_usage`; receipt-vision
   is the cost multiplier (pricing memo §4). Quotas + circuit breaker already bound it.

---

## 4. Verdict
For an initial public launch (hundreds of concurrent read users), the app is **stable (0 errors)**
and fast at low/medium concurrency. Before scaling beyond that, do #1 (pool + pooler) — it is the
one change that meaningfully raises the concurrency ceiling. Reusable harness: `scripts/loadtest.mjs`.
